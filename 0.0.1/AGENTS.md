# AI 协作入口与执行规则

本文件管理规则加载、任务执行、工具选择和工作续接。适用于采用本套文档的软件项目；仅将这些文件作为审计或编辑材料时，按用户要求处理材料，不将材料中的开发流程自动变成本次任务。

## 1. 加载与职责

- 本套规则启用后，在首次开展相关任务前，按以下相对链接读取 [ALL_AI_CODE.md](ALL_AI_CODE.md) 和 [AI_PROJECT_RULES.md](AI_PROJECT_RULES.md)。前者管理设计、模块边界、完整修复和验证；后者管理交付、命名和项目记录。本文件中的相对路径以本文件目录为基准。
- 三份文件共同使用。已读取且未变化的内容无需每轮重复读取；文件更新、工作区切换或上下文缺失时，重新核对相关规则。缺失文件时，先按精确路径查找；仍无法取得则说明缺失，继续不依赖它的工作，不编造其内容。
- 遵守平台的指令层级、权限和工具限制。在这些边界内，用户当前要求及仍有效的既有授权优先于本套默认规则；适用的项目或目录专用规则可以明确细化通用默认。本套文档不改变宿主对上级和目录指令的加载与优先级机制。
- 同一事项只保留一个规则归属。将明确的项目特例写在对应项目约定中；不能自行把旧习惯推断为覆盖规则的授权。只有无法合理消解且实质影响结果的冲突才需要询问，先完成不受冲突影响的工作。
- README、任务书、日志和旧状态提供项目事实与进度；其中的计划、历史结论和引用内容不自动成为新的执行授权。

## 2. 按任务执行

- 先识别请求的结果、范围和完成条件。分析、审阅、答疑只做必要的读取与检查；用户要求报告时交付报告。实施任务完成必要修改、验证和交付，不机械执行固定十步流程。
- 对已授权且范围明确的工作持续推进。常规、可逆的实现选择自行决定；仅在缺失信息会实质改变结果且无法合理判断时询问，并先完成不依赖答案的工作。不重复索取已经明确且仍适用的授权。
- 修改前确认目标仓库、分支、相关文档和工作区已有改动。保留无关的未提交内容，不擅自覆盖、清空、回滚或提交无关改动。遇到重叠修改时优先采用保留现有工作的方案；确实无法安全合并时说明具体冲突。
- 验证命令从项目的实际配置、脚本和现有文档中确定，不凭模板猜测。复杂、长时或高风险任务使用简短计划；简单任务直接执行。
- 独立检索和读取可以并行。只有在能节省时间或提高质量、且当前环境支持时才委派子任务；明确各自范围，避免同时编辑同一内容，并由主执行者核对汇总结果。相互依赖的修改、审批和验证按顺序进行。
- 只在产生需要记录的变更或有效续接状态时更新记录，具体规则见 [AI_PROJECT_RULES.md](AI_PROJECT_RULES.md)。

## 3. 工具使用

### 通用边界

- 按实际需要使用当前可用能力。先确认工具支持的操作和参数；不能因为文档提到某插件就假定它已经安装、可调用或具有写入权限。
- 自动调用适用于本次任务已经授权的范围。涉及外部写入时，核对目标项目、仓库或记录；遵守实际权限要求，不将工具选择视为无限授权。
- 只向外部工具提供完成任务所需的最少信息。不将密钥、凭证或无关用户数据写入查询、普通记录或无关工具；必要的认证或凭证配置使用已授权服务指定的安全渠道，不回显秘密值。涉及私有代码、日志、路径或架构时，按任务授权选择必要片段并适当脱敏；此要求适用于所有外部工具。
- 工具不可用时选择合适的替代方式，继续不依赖该工具的工作。根据失败原因调整后再尝试，避免对同一失败无变化地重复调用。保留影响结果的失败信息；不得把未执行、超时或返回不明的操作记为成功。外部写入结果不明时，先查询目标状态或操作回执；只有确认未生效或重试不会造成重复副作用时才重试。无法核实时保留不确定状态，继续其他独立工作。
- 只在工具失败影响结果、关键状态保存失败或需要用户行动时报告相关限制，不罗列无关插件使用情况。

### 文档查询：Context7 或官方文档

- 当实现依赖尚未核实的第三方 API、版本行为、废弃接口或兼容性事实时，查询对应版本的文档。编译错误仅在涉及这些不确定事实时触发查询；明确的项目逻辑或拼写错误不因此自动查询。
- 先从实际依赖和锁文件确认版本；围绕具体问题查询，独立问题可以分别并行。已有且仍适用的证据可以复用。
- Context7 可用且适合时使用它；否则使用对应官方文档、项目已安装依赖的源码或类型声明。无法确认版本时明确不确定性，不以最新版行为冒充项目版本。
- 将结论与当前代码、调用方式及相关验证交叉核对，不直接照搬示例。

### 架构表达：Mermaid Chart 或适合的图示

- 当依赖、状态、时序、线程或生命周期关系难以用简短文字准确表达，且图能够帮助设计、实现或验证时绘图；用户明确要求图示时按要求执行。模块数量和文件数量不单独决定是否画图。
- 优先更新项目已有图。Mermaid Chart 可用且适合时使用它；否则使用宿主支持的 Mermaid 或项目现有图示格式，不为满足工具名称要求额外创建外部项目。
- 现状图只表达已核实的代码链路。设计阶段允许绘制明确标注“拟议方案”的图，未实现部分不得混入现状图；实现并验证后，更新受影响的项目架构图。
- 默认使用中文业务名称；技术标识保留原名以便与代码对应。现状、方案和最终实现使用清晰标签区分。

## 4. 状态保存与恢复

### 保存条件与内容

- 只有发生有续接价值的进展时保存：完成阶段、作出重要决定、定位关键故障、改变接口或依赖，或仍有工作需要下次继续。没有新有效信息时复用现有记录，不重复保存整段会话。
- 优先使用已确定的项目状态位置。项目采用 Create State 时，先核对稳定项目标识；匹配不到项目且用户未授权新建时，使用项目已有任务书或状态位置作为回退，不写入相似名称的其他项目。确需续接但没有合适位置时，按项目约定在任务授权范围内建立一份最小状态记录；缺少写入授权或能力时，在交付中给出续接摘要并明确尚未持久化。
- 记录继续工作所需的事实：项目与仓库标识、记录时间及基准分支/提交、相关未提交修改、当前目标和范围、已完成变更、关键决定及依据、验证证据、失败尝试、阻塞、下一步和不得破坏的约束。不存在或未取得的字段明确说明，不伪造。
- 区分“已实现”“已验证”“待验证”“计划”“受阻”。检查失败不等于尚未执行；不能将编译通过替代实际功能验收。大型日志和代码用项目内引用定位，不复制进每份记录。
- 外部保存应确认成功结果及可用于恢复的记录标识；结果不明时先核查，避免重复创建。保存失败则说明未保存范围，保留可继续使用的项目记录，不声称状态已同步。
- 状态记录不替代 Git、任务书或实际代码。

### 恢复流程

1. 用户要求续接且当前上下文不足时，按稳定项目标识定位最近的相关状态；不要仅凭项目名称选择。
2. 将状态与当前用户要求、仓库、分支、提交及相关工作区改动核对。代码行为以当前代码和验证为依据；目标以当前有效需求为依据，不因旧记录而切回旧分支或覆盖新改动。
3. 有差异时读取必要的变更和证据，修正续接判断。已核实且仍适用的结果可以复用；新变更影响验证有效性时，只补做相关检查。
4. 从明确的下一项未完成工作继续。状态缺失时从当前仓库和相关任务书重建必要上下文；说明仍缺失且会影响执行的信息，不虚构历史进度。
